SELECT c.course_name,
       COUNT(e.enrollment_id) AS enrolled_count
FROM   enrollments e
JOIN   students  s  ON e.student_id = s.student_id
JOIN   courses   c  ON e.course_id  = c.course_id
WHERE  e.semester      = 'Semester 1'
  AND  e.academic_year = '2024'
GROUP BY c.course_name
ORDER BY enrolled_count DESC;

SELECT dc.course_name,
       COUNT(fe.enrollment_key) AS enrolled_count
FROM   fact_enrollment fe
JOIN   dim_course dc ON fe.course_key = dc.course_key
JOIN   dim_date   dd ON fe.date_key   = dd.date_key
WHERE  dd.semester      = 'Semester 1'
  AND  dd.academic_year = '2024'
GROUP BY dc.course_name
ORDER BY enrolled_count DESC;

WHY DOES THIS MATTER?
The schema design shapes the query, not the database engine

Same result, different work

Both queries return identical rows. The difference is not in what they answer - it is in how many tables the database must traverse and JOIN to get there.

Scale amplifies the gap

With 500 students this difference is invisible. With 50,000 students across ten years, the OLTP JOINs touch billions of row combinations. The warehouse star schema avoids this by pre-organising the data for analytical access.

The warehouse protects OLTP

Running heavy analytical queries directly on the OLTP system slows down the operational system for everyone using it. The warehouse gives analysts a separate, purpose-built system that does not compete with day-to-day operations.
